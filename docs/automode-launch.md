# Automode Bridge launch

After installing this repository as a Pi package, normal Pi registers `/automode` as an extension command. Extension commands are handled before ordinary model input, so the launch command is not submitted as a prompt.

```sh
npm ci
pi install .
```

The selector starts in Full-Auto with all four stages enabled. The minimum supported terminal size is 32 columns by 20 rows; labels, stage states, validation, and every control hint remain available at that size alongside Pi's reserved terminal rows.

- `Tab` switches Full-Auto/Half-Auto mode.
- Up, down, left, and right arrow keys move stage focus.
- `Space` toggles the focused stage only in Half-Auto, which defaults to Auto-Implement and Auto-Review enabled and the other two stages disabled.
- Half-Auto launches with any non-empty Stage baseline, including all four; an empty selection shows a validation message. A Half-Auto baseline containing all four Stages has the same initial operating state as Full-Auto while preserving the Half-Auto launch label.
- `Escape` cancels without launching a process.
- `Enter` confirms a valid configuration.

Confirmation serializes and validates the Automation Stage Configuration, passes it to the child as `AUTOMODE_STAGE_CONFIGURATION`, and passes a matching confirmation digest as `AUTOMODE_STAGE_CONFIGURATION_CONFIRMATION`. The bridge captures the active Pi provider and model as the process-local Main Session execution profile and passes it through `AUTOMODE_MAIN_EXECUTION`. The child rejects invalid launch data before Main Session startup. The bridge resolves nested working directories to the Git repository root, binds the child to the exact Pi package installation running normal Pi, gives the fresh child process the inherited terminal through the proven handoff seam, and exits normal Pi with the child's status. Repository Pi dependencies are development-only compatibility pins, not an independent Automode runtime.

After every startup check and canonical-resource attestation succeeds, the child persists a Coordinator-bound Automode Run Record at `<git-common-dir>/automode/automode-run.json`. The record contains the durable Coordinator identity, fixed launch-baseline Automation Stage Configuration, and explicitly allowlisted project skill files; it is not the Automode Capability Profile. Main Session and Panel execution profiles are process-local and never participate in Run Record matching. A restart automatically removes the obsolete `defaultReviewerExecution` field from older records. Process-local Automation Stage Operating State is also excluded. Native Main Session history remains isolated under `~/.pi/automode/<repository-key>/sessions`, and the baseline configuration is appended to Main Session state. Restarting the same Automode Run from another Pi home or linked worktree with different baseline settings fails; `/new`, `/resume`, `/fork`, and `/clone` replacement paths are cancelled.

`src/capability-session.ts` constructs only the startup Automode Capability Attestation Session and disposes it before Main Session creation. After the run record exists, `src/coordinator.ts` hosts discovery and supervision while `src/ticket-session.ts` launches one independent full child process per item. Each child creates or resumes controlled persistent Pi history and receives one deterministic canonical skill command; the Main Session never performs ticket work.

Before work discovery, startup fails closed unless all of these checks succeed:

- Git identifies the same repository root selected by the Bridge.
- `gh` is authenticated for `github.com`, resolves the same repository as the local `origin`, and grants write permission for any Stage that may be enabled process-locally. Startup derives the actor from the active authenticated account rather than issuing a separate REST `/user` request, and polls transient GitHub HTTP or connection failures for up to 30 seconds before failing closed.
- Pi can resolve the process-local Main Session profile from its built-in catalogue or normal `models.json`, plus the fixed ordinary Ticket Session profile and both fixed Panel profiles, regardless of the launch baseline.
- Pi's public command registry and resource diagnostics show exactly one canonical command per controlled skill. Every extension-owned Automode Stage Skill is preloaded so re-enabling a Stage does not change the attested capability boundary.
- The repository's Agent guidance, domain context, and directly referenced tracker/domain documents load while ambient extensions, skills, prompts, themes, and project settings remain excluded; the controlled `/fast` extension explicitly reuses normal Pi's synchronized OpenAI fast-mode state.
- The repository Coordinator lock is available.

The durable Coordinator identity, Automode Run Record, and live lock are stored under the repository's Git common directory so linked worktrees and processes using different home/config roots still share one fixed run. A live `coordinator.lock` permits only one Coordinator process per repository; a clean stop removes the lock, and a restart reuses the identity and fixed launch baseline while restoring every process-local Stage to `ON` or `OFF` from that baseline. Each Main Session uses the provider and model active in the Pi process that invoked `/automode`. Ordinary Ticket Sessions use Pi / `openai-codex/gpt-5.6-sol` / high reasoning. Auto-Grilling and Auto-Review use two seats: Pi / `openai-codex/gpt-5.6-sol` and Pi / `github-copilot/claude-fable-5`, both at high reasoning. Project executable skills load only when the project is explicitly trusted and each path is explicitly allowlisted.

After startup checks but before discovery, the Main Session starts the Coordinator dashboard on loopback port `41738` when available and otherwise asks the operating system for a free loopback port. Dashboards for different repositories can therefore run concurrently. Each dashboard adopts an existing Tailscale root handler that already targets its exact local URL or adds a root handler on an unused HTTPS port. Shutdown removes only that owned root handler, preserving unrelated Tailscale Serve configuration. Exposure failure keeps the exact localhost URL working and publishes the error in both supervision surfaces. The compact Main Session status card and browser consume the same replacement projection, including repository/run identity, all four Stage states, candidate/active/queued/held/retrying/exhausted totals, and successful/next poll timing. The TUI also shows the exact local and remote links plus the `/drain` and `/exit` lifecycle commands; detailed lanes and activity remain browser-only. Automode does not intercept `Ctrl-C`, so Pi retains its default TUI behavior.

After the dashboard is listening, the Coordinator restores Automation Stage Operating State from the launch baseline, reconciles surviving bookkeeping before new claims, takes a complete GitHub snapshot, and polls every 30 seconds. `ON` permits discovery and dispatch. Switching off a Stage enters `DRAINING` while active Ticket Sessions settle, then `OFF`; a Stage with no active Ticket Sessions turns `OFF` directly. `DRAINING` and `OFF` prevent new dispatch, re-enabling requests a full scan, and all four Stages may remain `OFF` while the Coordinator monitors. Material changes trigger a full `ON`-Stage scan in Auto-Triage, Auto-Grilling, Auto-Implement, then Auto-Review precedence. Unrelated eligible items launch without a software concurrency cap. Every item has one updateable bookkeeping comment, at most five attempts, fresh tracker proof after a clean turn, and preserved diagnostics on exhaustion. Prototype waiting is idle until external material feedback changes the snapshot. Browser refresh requests an immediate full scan; browser drain is graceful and idempotent. In the Main Session, `/drain` starts a repository-wide graceful drain and exits after active Ticket Sessions settle. `/exit` immediately force-stops active Ticket Sessions, then exits after Coordinator and dashboard cleanup. Dashboard shutdown completes before the Coordinator lock is released.

Auto-Implement uses deterministic branches and worktrees under `.worktree`; recovery resumes surviving sessions and reconstructs missing worktrees from branches. Auto-Grilling and Auto-Review use the two fixed Panel seats with identical immutable context, hidden peers, and read-only advisory tools. Review workspaces are pinned to the exact pull-request head and checked for pushability before fixes. Successful review cleanup is gated on a completed merge.

## Validation

```sh
npm test
```

The suite includes a real-Pi RPC smoke test proving command registration and pre-model handling, selector behavior and minimum-size readability checks, and real-Pi PTY walkthroughs of the Full-Auto and Half-Auto happy paths. The PTY walkthroughs prove no model turn starts, the child is fresh, nested launch directories resolve to the repository root, and the confirmed launch baseline remains intact. A black-box `/automode` acceptance additionally follows the rendered TUI link into the real HTTP dashboard, observes a running Stage Candidate and live structured activity, requests graceful browser drain, and proves clean process exit. A process-boundary test tampers with the serialized environment payload and proves startup rejects it. Stage-contract tests prove separate process-local `ON`/`DRAINING`/`OFF` state, monitor-only state, restart restoration from the baseline, reactive poll timing, and repository-wide drain transitions. Coordinator tests cover polling, precedence, independent dispatch, retries, recovery, prototype waiting, and shutdown; dashboard tests cover concurrent loopback allocation, isolated Tailscale handler ownership, and the secured command boundary; process tests exercise persistent Ticket Session IPC; real Git fixtures prove deterministic worktree creation/recovery/cleanup; and a deterministic Full-Auto journey advances representative work through all four stages to merge.
